01 / 修訂後的核心結論

這是「遊戲引擎客戶端」職缺，不是把圖片放在網頁上的前端

L 的房間、寵物、人物、家具、建設與任務表現，將由遊戲引擎（或具備遊戲場景管理能力的 2D Web 遊戲框架）運作。系統需要場景樹、物件生命週期、動畫狀態、素材打包、遊戲互動與儲存同步，不能用普通網站切版能力取代。

建議仍以 3 名新增工程師啟動正式 MVP，但兩名前端的組合要改成「1 名 2D 遊戲引擎客戶端主力＋1 名懂引擎整合的學習互動前端」。此外，必須有 2D 動畫／技術美術包件支援，不可以把素材產線算成工程師順手會做的事情。

先不要做

引擎方案與人力如何對應？

不同引擎會影響招募語言：Cocos Creator 主力需要 TypeScript 與 Cocos 節點／預製物件；Unity Web 主力需要 C#／Unity Scene／Prefab 與 Web 輸出實務；Phaser 主力需要 TypeScript 與 2D 遊戲流程。詳見下一章，不再把 PixiJS 純渲染能力等同於完整遊戲引擎能力。

03 / 2D Web 引擎選型與徵才分岔

先決定「做遊戲」的技術路線，再寫前端職缺

對 KALM L 這種需長期佈置與角色演出的遊戲視覺系統，Cocos Creator、Phaser、Unity Web 都可能完成需求，但「有 Web 輸出」不等於相同的效能、打包尺寸與人才成本。優先要測的是本產品自己的低階裝置載入、素材迭代與學習面板協作。

首選評估 A｜完整視覺編輯器

C Cocos Creator 3.x

2D 場景、節點、Prefab、動畫、材質、資產管理與 Web Desktop／Mobile 發布整合。對需要反覆編輯房間及大量家具的產品，對美術／設計協作較直接。

招募語言：TypeScript、Cocos Creator 場景節點／Prefab／Animation、UI 系統、資源 Bundle、Web 發布與手機效能。
適合情況：以 2D 居家場景與角色展示為重心，且需要編輯器工作流。[S17] [S18]
首選評估 B｜純網頁 2D

P Phaser 3

專為 HTML5 2D 遊戲設計，支持 WebGL／Canvas、TypeScript。遊戲場景邏輯可直接與 React／Vue 等 Web UI 整合；編輯器導向的素材工作流則需自行補齊。

招募語言：TypeScript、Phaser Scene／Game Object／Tween／Animation、資源載入、事件與座標系、Web UI 橋接。
適合情況：純網頁平台整合優先、可接受較多自行寫工具的工程投入。[S15] [S19]
有條件選用｜桌面優先、既有 Unity 人才

U Unity 6 Web

有完整 Scene、Prefab、Animator、Sprite、Tilemap、C# 等成熟工作流；能編譯 Web，但 Unity Web 應用的首載、記憶體與手機體驗，必須用目標裝置實測，不能只因 Unity 熟悉就認定划算。

招募語言：C#、Unity 2D、Animator、Sprite Atlas／Addressables、Web Build、Unity ↔ JavaScript 交互。
適合情況：桌面版為主要目標或已有 Unity 工程資產，並完成手機可行性實測。Unity 6 文件列出部分手機瀏覽器支援，不宜沿用舊版「完全不支援行動端」的說法。[S20]
渲染方案｜不是等價遊戲引擎

Pi PixiJS

適合高效率 2D 渲染及動畫展示，但 Quest、場景物件管理、互動規則、編輯器工具、存檔等需要自行組裝。若 L 要成為真正的 2D 生活遊戲，不建議僅因它容易繪製畫面就首選。

招募語言：TypeScript／Canvas／WebGL、渲染架構、自行組件化；工程整合成本需要另估。[S16]

成本怎麼算，哪些不是政府規定的固定比例？

雇主退休金提繳的法定下限為適用月工資的 6%；勞保普通事故保費雇主負擔 70%，健保雇主負擔 60%，且還有就業保險、職災保險與投保級距。[S11] [S12] [S13] [S14] 試算器的 11%／13%／15% 是用於概算的「整體雇主額外費用預備率」，不是任何一條法定比率；正式聘僱應由會計依適用投保薪資與個別身分逐人計算。

這裡把 1 個月年度獎金以每月 1/12 預提，目的只是預算規劃，不是主張法規保證有 13 薪。實際年終、績效獎金、特休、資遣準備、硬體汰換與租金要依公司制度補列。本估算沒有將雇主保費精確拆到投保級距，也沒有計入行銷成本或大規模 AI 推論用量。

10 / 工程責任邊界

看似一個餵貓動作，實際至少有八個交界

步驟應由誰做工程交付物
1. A 回傳能力狀態A 產品／API 擁有者有版本、有效期、信心欄位的評鑑資料
2. L 解釋狀態L 後端＋AI 應用明確的規則表／必要時模型輔助，不是任意文字
3. Quest 選擇L Quest Director學習目標、教學方式、模板 ID、時間與難度
4. 房間產生需求遊戲引擎主力＋學習整合前端引擎中的貓碗 GameObject／事件；Quest 面板橋接及場景動畫
5. K 提供教材K 擁有者教材／題目、答案與來源、可追溯版本
6. User 學習學習整合前端＋L 教學流程DOM 或引擎內 UI：回想／閱讀／測驗；統一事件與恢復機制
7. 驗證與發獎A 判斷＋L 後端伺服器驗證、獎勵防重複、完整事件紀錄
8. M 存檔M 擁有者／L 後端能力歷史、任務與房間狀態，支援重進與回復

你們應該要求工程師先對齊的資料契約（示意）

AssessmentResult { learner_id, skill_id, score, level, error_type, hint_dependency, confidence, assessed_at } ↓ LearningStrategy { target_skill, activity_type, difficulty, duration, evidence_requirement } ↓ Quest { quest_id, world_need, game_object_id, learning_activity_id, status, reward_policy, version } ↓ QuestAttempt { quest_id, attempt_id, validated_by_A, event_time, grant_id } ↓ WorldState { room_id, furniture_state, pet_state, save_version } 備註：這是 L 應與各系統討論的設計契約，不是聲稱 KALM 目前已有上述資料欄位。

最大的後端坑不在貓動畫，而在使用者切換裝置、網路中斷、多次送出時，任務到底算不算成功、貨幣能不能重複領、A 的結果是否仍有效。因為這些都會真實影響學習與世界狀態，所以後端應由能獨立負責的工程師帶。

引擎與 Web 前端之間的「事件橋接」

GameEngine: PetBowlClicked { object_id, scene_id } → WebApp: OpenLearningQuest { quest_id } → Server: AttemptValidated { attempt_id, evidence_version } → Server: RewardGranted { grant_id, inventory_delta, world_delta } → GameEngine: PlayPetFeeding { pet_id, animation_id } → SavedWorld: { save_version, world_state } 此為建議介面示意。事件名稱與欄位應由團隊訂成正式契約。

Unity 路線需處理 Unity ↔ JavaScript 的跨執行環境溝通；Cocos／Phaser 則可透過 TypeScript 事件系統與 Web UI 協作。無論引擎路線，玩家不能自行宣告「我已答對」就獲得貨幣：畫面動畫是結果呈現，不是交易權威。

11 / 徵才規格與面試操作

招聘公告要寫「會用遊戲引擎交付 Web 2D 作品」

前端 1｜引擎客戶端

職稱：2D 遊戲引擎工程師（Cocos Creator／Unity 2D Web／Phaser 擇一）。

必要：至少一套主引擎實作、Scene／Prefab、2D 動畫、拖曳佈置、Web build 與跨裝置優化。

月薪：55–70K；有完成作品比修課證書重要。

前端 2｜學習／引擎整合

職稱：互動產品前端工程師（TypeScript／遊戲引擎整合）。

必要：Quest／教材／答題 UI＋API，能處理引擎事件、遊戲與 UI 狀態同步。

月薪：42–55K；非單純 CSS 切版。

後端｜Quest／存檔

職稱：後端工程師（學習任務／遊戲狀態／A／K／M 整合）。

必要：受信任的任務發獎、存檔、冪等性、權限與資料一致性。

月薪：48–65K；不要求自建大型遊戲伺服器。

主引擎候選人的四關

檢查看什麼成果未通過代表什麼
現有作品一個能在瀏覽器真的操作的遊戲作品、執行影片與部分程式碼解說只有作品截圖或 Unity 編輯器截圖，不能證明能交付
場景／動畫展示 Scene／Prefab、動畫狀態與家具拖曳、狀態保存只有圖片轉場，缺引擎核心能力
Web 與裝置知道自己的 Web Build 首載問題、iOS/Android 相容性、效能診斷方法只做桌面 Editor Play，沒有正式發布經驗
團隊協作能說明素材導入規格、怎麼讓第二名前端串事件、怎麼讓美術自行換資產單人 Demo 技能不代表可持續營運

現場技術討論以 60–90 分鐘為佳。若要求完整「房間＋貓＋家具＋Web」2 天試作，應提供素材與合理試作費，或以已完成的候選人作品替代，不以免費實作取得商用程式。

哪些情況才要加引擎工程師或技術美術？

場景和動畫待辦持續堆積

若新增玩法與修效能排到下一季，才考慮第二名引擎客戶端。

素材無法自主量產

若每件家具、換裝都要工程師重新拆圖改程式，優先補技術美術與資產工具。

教學 UI 與引擎互相卡住

把學習互動前端的引擎 API／事件橋接能力補強，不是加一名純切版。

K／A／M API 對接拖延

優先把平台後端／AI 整合端固定窗口及工時補齊。

12 / 引擎正式驗收清單

驗收標準要包含場景、動畫、產線、學習與發布

類別不可省略的驗收項目成果判定
遊戲引擎提供原始工程專案、引擎版本、資產與設定，不是只有打包後網頁他人可重新 Build 出相同功能
2D 場景家具遮擋／拖曳吸附／物件擺放／紙娃娃部位排序實際操作、重開後狀態相同
動態演出貓咪從待機→靠近食物→進食→滿足→返回；正確播放並可打斷動畫不突跳、不靠影片假裝互動
素材產線技術美術提交一組新家具及動作，按規格導入不需要大量客製硬改程式
Web 裝置Desktop Firefox／Chrome、iOS Safari／Android Chrome 首載與使用流程每種目標瀏覽器均有實機紀錄；不先宣稱固定 FPS
A → L給同分不同錯因的評鑑輸入Quest 內容與學習行為實際不同
學習與發獎錯答、中斷、快速重送、雙頁登入、重複按鈕不重複發獎、世界狀態最終一致
營運交接建置文件、事件契約、除錯工具、回退方案第二位工程師可修改並部署

以上為本報告擬定的驗收條件，屬產品需求而非研究證據。最低裝置規格、容量與載入上限，應在選定引擎的技術驗證後訂出數值。

13 / 最終人事採購建議

三名工程師可以，但其中第一名必須是真正的遊戲引擎開發者

建議編制：① 2D 遊戲引擎客戶端工程師 1 名（月薪中心 6.2 萬）；② 學習互動暨引擎整合前端 1 名（4.9 萬）；③ Quest／遊戲狀態後端 1 名（5.7 萬）。AI 從 KALM 共用 0.5 人力，美術＋技術美術委外約 4.2 萬／月預備額。完整 MVP 估 7–10 個月，主要看資產產線與 A／K／M 能否供應穩定介面。

若公司目前已經有熟 Cocos Creator 或 Unity Web 的遊戲工程師，應優先使用現有人才／技術堆疊減少招募；若沒有，招聘公告須直接寫明 Web 2D 引擎作品與實作經驗，不能先請普通網頁前端再希望他入職後從零學會。

人數不是最大變動，職務能力與美術管線才是

舊方案把第一名前端比較接近「視覺互動 Web 工程師」，現在正式更正為「遊戲引擎客戶端主力」。第二名前端也要能協作引擎事件；技術美術是可明確採購的工作；薪資、外包額與工期已同步調整。這才符合 L 要是一個持續生活、可遊玩的 2D 世界，而不是一張動畫網頁。
