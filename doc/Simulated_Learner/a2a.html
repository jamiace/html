A2A / 多 Agent 協作頁

A2A 的正確定位

A2A 是 Agent-to-Agent 的通訊協定，用來讓不同代理發現彼此、接受任務、交換狀態與交付產物。它不是把知識直接訓練進別的模型的方式。

如果你的目標只是「讓某個 LLM 學會這套方法」，先給它明確的技能規範與任務契約就好，不必一開始就上 A2A。

什麼時候值得用 A2A？

  • 要把人物設計、場景執行、證據驗證拆成不同代理。
  • 需要跨團隊、跨框架或跨服務協作。
  • 希望 Agent 能被目錄發現、可替換、可擴充。

建議的三個 Agent

Agent責任不該做什麼
Persona Designer根據目標建立人物、狀態模型與假設不要直接操作正式系統
Scenario Runner依核准規則實際執行瀏覽器 / API 測試，輸出事件與截圖不要臨場任意編故事更改人物
Evidence Reviewer比對事件、日誌與目標，回報通過 / 失敗 / 未驗證不要把 coverage 數據包裝成真人行為

典型任務流

  1. 主代理送出 design_personas。
  2. 收到 persona 後由人或規則檢查器先驗收。
  3. 送出 execute_scenario，指明是 coverage 或 behavior。
  4. Runner 交付 events.jsonl、截圖、可重現步驟。
  5. 送出 review_evidence。
  6. Reviewer 回傳已證實結果、限制、下一輪調整建議。

最低協作守則

  • 每個事件都要標示 synthetic=true。
  • mode=coverage 與 mode=behavior 的統計不得混用。
  • 必須保存 seed、規則版本、模型版本與執行環境。
  • 最終驗證必須來自系統真實回應，不是代理口頭說成功。
  • 若正式站涉及付費或資料修改，必須有人員授權。

Agent Card 概念範例

{
  "name": "persona-designer",
  "description": "Designs stateful simulated learners/users",
  "supportedInterfaces": ["tasks", "artifacts"],
  "skills": [
    "design_personas",
    "build_behavior_policies",
    "declare_limitations"
  ]
}

欄位名稱請依當下官方 A2A 規格與 SDK 為準。這裡是概念示意，不代表可直接部署的完整服務。
