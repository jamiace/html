進階者：建模、事件與驗證

進階版核心：把人物寫成「有狀態的系統」

如果你已經會做簡單人物設定，下一步不是「增加角色數量」，而是提升模型的可解釋性與可重現性。推薦用這個循環：

state -> trigger -> candidate actions -> decision -> product feedback -> state update

這讓你不再只是寫故事，而是建立一個能夠在多日、多情境下穩定執行的行為模型。

何時算進階？

  • 你開始追蹤可變狀態，而不是只看固定 persona。
  • 你知道 coverage 與 behavior 要分開。
  • 你會保存亂數種子與規則版本。
  • 你能說清楚哪些是已證實、哪些只是模擬觀察。

建議追蹤的狀態

狀態用途典型變化
interest是否還願意啟動重複內容太多就下降；新鮮回饋可上升
confidence對自己是否做得到的感受連續成功上升；連錯幾次下降
familiarity對產品流程的熟悉度使用越多越高，跨版本大改可能下降
fatigue暫時性疲勞與抗拒長流程、長閱讀、連續失敗會增加
memory知識保留狀態隨時間遺忘，複習或正確回想上升

事件記錄最低欄位

{
  "run_id": "2026-11-23-demo-01",
  "persona_id": "P03",
  "timestamp": "2026-11-23T19:31:00+08:00",
  "mode": "behavior",
  "trigger": "pet_hungry",
  "action": "answer_vocab_quiz",
  "result": "2_correct_1_wrong",
  "state_delta": {"confidence": -0.05, "memory": +0.02},
  "seed": 917213,
  "synthetic": true
}
這個 schema 不只給人看，也可以直接供 log pipeline、驗證器與回放工具使用。

驗證框架：你究竟在證明什麼？

類型你能證明的事你不能直接證明的事
功能正確性流程真的走得通、錯誤能重現、資料有記錄真人會不會喜歡
行為差異不同 persona 規則可產生可解釋差異真實人口比例、自然留存率
模型敏感度改動某參數時結果如何變動市場規模、真實產品 KPI

進階者最常犯的錯誤

錯誤 1：用同一套模擬結果同時報告流程覆蓋與自然留存

如果人物被迫每天執行固定場次，那就已經不是自然行為。這樣的數據可以拿來看系統有沒有漏記錄，不能拿來說明自然使用情況。

錯誤 2：讓 LLM 每一步即興決策，卻沒有固定規則與版本

這會讓你無法重現，也無法區分是產品有問題，還是模型當下心情不同。

錯誤 3：讓模擬器與被測系統共用同一套假設

如果產品的推薦規則與模擬器的評估規則完全相同，你可能只是在做循環驗證，看見的「成功」可能只是自我證明。
